# Архитектурные решения и уточнения требований

Здесь записано, как я трактовал места спецификации, которые были противоречивы или недоопределены.
Формат: решение, почему так, что можно поменять. Нумерация сквозная по фазам.

## Фаза 1: каркас бэкенда

### D1. FluentAssertions 7.x вместо 8.x
С версии 8 FluentAssertions распространяется по коммерческой лицензии (Xceed). Используется 7.2.x,
последняя ветка под Apache-2.0, API для наших тестов тот же.

### D2. Без MediatR, тонкие эндпоинты и сервисы фич
MediatR тоже стал коммерческим. Vertical slice устроен так: `Finance.Application/Features/<Фича>` содержит
модели, валидаторы, `*Writer` (правила записи без `SaveChanges`) и `*Queries` (чтение).
Эндпоинты Minimal API в `Finance.Api/Endpoints/<Фича>Endpoints.cs` оркеструют `writer → SaveChanges → query`.
Writer'ы переиспользуются синхронизацией (фаза 4): правила валидации у REST и `sync/push` общие.

### D3. Application зависит от EF Core и Npgsql
`IAppDbContext` отдаёт `DbSet<T>`, а запросы используют `EF.Functions.ILike` и сравнение кортежей
`(date, id) < (@d, @id)` для курсорной пагинации. Абстрагировать это ради смены СУБД нецелесообразно:
проект завязан на PostgreSQL. Domain от EF не зависит, прогноз будет чистым доменным сервисом.

### D4. Валидация: FluentValidation внутри сервисов
Валидаторы вызываются в writer'ах и сервисах (`ValidateAndThrowAsync`), а не фильтром эндпоинта.
Так одна и та же проверка срабатывает и для REST, и для sync. Ошибки отдаются как ProblemDetails 400
с `errors` (ключи в camelCase) и `errorCodes`.

### D5. Коды ошибок и статусы
Каждый ProblemDetails содержит расширение `code` (стабильный машинный код):
- 400 `validation_failed`, `invalid_json`, `bad_request`;
- 401 `invalid_credentials`, `invalid_refresh_token`, `unauthorized`;
- 404 `not_found`: ресурс из URL не найден. Чужие данные тоже дают 404, чтобы не раскрывать их существование;
- 409 конфликт с состоянием: `id_conflict`, `email_taken`, `account_has_transactions`, `category_has_children`, ...;
- 422 нарушено бизнес-правило или ссылка в теле указывает на несуществующую сущность:
  `account_not_found`, `category_kind_mismatch`, `category_depth_exceeded`, `transfer_to_amount_required`, ...

### D6. ID генерирует клиент (UUID v7), но в REST можно не передавать
Клиентский `id` проверяется: это должен быть UUID v7. Если в `POST` его нет, сервер генерирует v7 сам.
Это удобно для ручных вызовов из Scalar и не мешает offline-first: мобильный клиент всегда передаёт свой id.
Занятый id (своей, чужой или удалённой сущностью) даёт 409 `id_conflict` с одинаковым текстом во всех случаях.

### D7. Version: глобальная sequence и advisory lock на пользователя
`SaveChangesAsync` для каждой изменённой пользовательской строки берёт `nextval('global_version_seq')`.
Перед этим в той же транзакции берётся `pg_advisory_xact_lock(<ключ пользователя>)`.
Без блокировки транзакция с меньшей версией могла бы закоммититься позже транзакции с большей,
и `sync/pull?since=` её пропустил бы. С блокировкой порядок коммитов одного пользователя совпадает с порядком версий.
Записи разных пользователей не блокируют друг друга. Жёсткое удаление пользовательских сущностей запрещено
на уровне контекста: удаление только мягкое (`DeletedAt`) и тоже получает новую версию.

### D8. Мультитенантность: именованные фильтры EF Core 10
Два фильтра на каждой пользовательской сущности: `Tenant` (`UserId == текущий`) и `SoftDelete`.
Без аутентифицированного пользователя (фоновые задачи) фильтр подставляет `Guid.Empty`, то есть по умолчанию
не видно ничего. Задачи явно отключают фильтр: `IgnoreQueryFilters([QueryFilters.Tenant])`.
Дополнительно `SaveChanges` бросает исключение при попытке записать сущность другого пользователя.

### D9. Курсы валют
- Хранится курс **за 1 единицу**: `Rate = Cur_OfficialRate / Cur_Scale` (`numeric(28,14)`), источник `NBRB`.
- Конвертация любых валют идёт через BYN, округление (ToEven) **один раз** в конце, без промежуточного
  округления до копеек BYN.
- Для даты без курса берётся ближайший предыдущий. Если дата раньше всей истории, берётся самый ранний
  известный курс. Если по валюте нет ни одного курса, ответ 422 `exchange_rate_not_found`.
- «Сегодня» для НБРБ считается по Минску (`Europe/Minsk`).
- Hangfire-задача `exchange-rates` запускается каждые 6 часов (`15 */6 * * *` UTC) и идемпотентна (upsert по дате и валюте).
  При старте она ставится в очередь, если курсов за сегодня нет.
- Дополнительно при старте догружаются пропущенные дни за последние `ExchangeRates:BackfillDays` (по умолчанию 30).
  Без истории конвертация прошлых операций шла бы по слишком позднему курсу.
- Вся история курсов кэшируется в памяти (IMemoryCache, 1 час, сброс после импорта): это несколько тысяч строк.

### D10. Баланс счёта
`InitialBalance + Σ` по проведённым (`Cleared`) неудалённым транзакциям: Income `+Amount`, Expense и исходящий
Transfer `−Amount`, входящий Transfer `+ToAmount`. Запланированные (`Planned`) на баланс не влияют.
Для быстрого запроса есть два частичных покрывающих индекса:
`(account_id, date) INCLUDE (user_id, type, amount) WHERE status='Cleared' AND deleted_at IS NULL` и аналогичный по
`to_account_id`. Фильтр по `date` нужен для «баланса на дату» (net worth в фазе 3).

### D11. Правила удаления и изменения
- Счёт с транзакциями (в том числе входящими переводами) удалить нельзя: 409 `account_has_transactions`, предлагается
  архивировать. Удалённый счёт снимается с `DefaultSpendingAccountId`.
- Валюту счёта с транзакциями менять нельзя: 409 `account_currency_locked`, иначе суммы потеряют смысл.
- Категорию нельзя удалить, если у неё есть подкатегории или транзакции (409). Тип (Income/Expense) нельзя менять
  у системной категории, у категории с подкатегориями или с транзакциями.
- Транзакции в архивные счета и категории разрешены (например, задним числом).

### D12. Переводы
`CategoryId` у перевода всегда `null`. Для счетов в одной валюте `ToAmount` должен совпадать с `Amount`; если его
не передали, он подставляется автоматически. Комиссию стоит записывать отдельным расходом. Для разных валют
`ToAmount` обязателен.

### D13. Системная категория «Без категории»
Для импорта (фаза 8) нужна категория-заглушка, а у Income/Expense категория обязательна.
Поэтому при регистрации создаются «Без категории» для расходов и для доходов с `SystemCode = "uncategorized"`.
Их нельзя удалить, сделать подкатегорией или сменить им тип, а переименовать можно.

### D14. Фильтры списка транзакций
Фильтр по `accountId` включает входящие переводы на счёт. Фильтр по `categoryId` включает подкатегории.
Фильтр `tag` — точное совпадение без учёта регистра (теги и так дедуплицируются без учёта регистра).
`search` — подстрока в заметке без учёта регистра (GIN trigram индекс). Пагинация по ключу `(date desc, id desc)`,
`limit` от 1 до 200, по умолчанию 50.

### D15. Теги и заметки
До 20 тегов по 50 символов. Пробелы по краям обрезаются, пустые выкидываются, дубликаты без учёта регистра
убираются (сохраняется первое написание). Заметка до 500 символов, пустая хранится как `null`.

### D16. Аутентификация
- Access token: JWT HS256 на 15 минут (`sub` = userId). Refresh token: 32 случайных байта, в БД хранится только SHA-256.
- Refresh живёт 30 дней и продлевается при каждой ротации. Повторное использование уже ротированного токена
  отзывает всю «семью» (все токены этого входа). Другие входы пользователя (другие устройства) не затрагиваются.
- Окна ожидания для параллельных refresh нет, поэтому клиент обязан выполнять refresh последовательно
  (в dio interceptor — один refresh за раз, остальные запросы ждут его).
- `logout` принимает refresh token и работает без access token (он мог истечь). Всегда отвечает 204.
- Логин по несуществующему email всё равно проверяет пароль на фиктивном хеше, чтобы время ответа не выдавало,
  существует ли email.
- На `/auth/*` стоит rate limit: 20 запросов в минуту с одного IP (настраивается).

### D17. PATCH /me — JSON Merge Patch (RFC 7386)
Отсутствующее поле не меняется, `null` очищает nullable-поле (`defaultSpendingAccountId`), для обязательных
полей `null` даёт ошибку валидации. Порог тревоги `lowBalanceThreshold` хранится в minor units базовой валюты,
по умолчанию 0 (тревога, когда баланс < 0).

### D18. Значения по умолчанию для пользователя
Базовая валюта BYN, часовой пояс `Europe/Minsk`, `FirstDayOfMonth = 1`. Часовой пояс проверяется по IANA-базе.

### D19. Enum'ы хранятся строками
Читаемые данные и миграции без привязки к порядку членов enum. На wire тоже строки (`"DebitCard"`).

### D20. Миграции применяются при старте API
`Database:MigrateOnStartup=true` (по умолчанию). Для одного инстанса на VPS это проще всего.
При горизонтальном масштабировании надо выключить и применять миграции отдельным шагом (`dotnet ef database update`
или EF bundle).

### D21. Деплой на VPS
`deploy/docker-compose.yml`: PostgreSQL 17 (порт наружу не открыт), API, Caddy с автоматическим HTTPS
(Let's Encrypt) и ежедневный бэкап (`prodrigestivill/postgres-backup-local`: хранятся 7 дневных, 4 недельных
и 6 месячных копий в `deploy/backups`). Секреты лежат в `deploy/.env` (в git не попадает).
Hangfire Dashboard, OpenAPI и Scalar включены только в Development.

### D22. Порты для локальной разработки
На машине разработчика порты 5432–5435 и 8080 оказались заняты, поэтому dev-compose публикует PostgreSQL на `5445`,
а API на `5080` (`POSTGRES_PORT` и `API_PORT` переопределяют их).

### D23. Логи
Serilog: в Development человекочитаемый вывод в консоль, в остальных окружениях компактный JSON
(`RenderedCompactJsonFormatter`), его удобно собирать `docker logs` и любым агрегатором.

### D24. Npgsql без GSS и логи DataProtection
Npgsql 10 по умолчанию пробует GSS-шифрование через Kerberos (`libgssapi`), которого нет в образе. В строку
подключения автоматически добавляется `Gss Encryption Mode=Disable`, если она не задана явно.
DataProtection в приложении не используется (нет cookie и antiforgery, JWT подписывается своим ключом),
поэтому его предупреждения о неперсистентных ключах в контейнере скрыты уровнем логов `Error`.

## Фаза 2: регулярные платежи, бюджеты, цели

### D25. У правила есть название
В макете «Регулярные» правила подписаны («Мобильная связь»), а в ТЗ у шаблона есть только `Note`. Добавлено поле
`RecurringRule.Name` (обязательное). У материализованной транзакции `Note = Note ?? Name`, поэтому в списке операций
платёж узнаваем.

### D26. Семантика расписания
Периоды отсчитываются от `StartDate`:
- `Daily`: каждые `Interval` дней от StartDate;
- `Weekly`: в `DayOfWeek` (по умолчанию день недели StartDate), первое вхождение — ближайшее не раньше StartDate;
- `Monthly`: в `DayOfMonth` (по умолчанию число StartDate) каждые `Interval` месяцев, считая от месяца StartDate;
- `Yearly`: в месяце StartDate, `DayOfMonth` или число StartDate.

Число больше длины месяца даёт последний день (31 → 30 апреля, 29 февраля → 28 февраля в невисокосный год).
Вхождения раньше StartDate (возможны в первом месяце) и позже `EndDate` (включительно) отбрасываются.
`DayOfMonth` допустим только у Monthly/Yearly, `DayOfWeek` — только у Weekly.

### D27. Материализация
- Hangfire-задача `recurring-transactions` запускается **каждый час** (`5 * * * *`): «сегодня» у пользователей в разных
  часовых поясах наступает в разное время. При старте приложения она тоже ставится в очередь.
- Создаются Planned-транзакции за сегодня плюс за 7 дней назад: это добирает дни, пока сервер не работал.
  Дни раньше даты создания правила не создаются никогда, иначе правило с давним StartDate завалило бы пользователя
  старыми платежами.
- Сразу после создания или изменения правила материализация запускается для этого пользователя, так что платёж
  «на сегодня» появляется мгновенно.
- Вхождение материализуется один раз. Признак — существующая транзакция с тем же `(RecurringRuleId, RecurrenceDate)`
  в любом статусе, включая удалённые; это поддерживает уникальный индекс. Проверка и вставка выполняются под
  advisory-блокировкой пользователя, поэтому задача и запрос не гоняются друг с другом.
- Ошибка одного пользователя логируется и не останавливает обработку остальных.

### D28. Детерминированные id вхождений (UUID v7)
Id транзакции вхождения вычисляется из `(ruleId, date)`. Сервер и офлайн-клиент получают один и тот же id,
и синхронизация не создаёт дубликатов. Алгоритм (клиент на Dart повторяет его побайтно):
- `seed = "<ruleId в формате D, нижний регистр>|<yyyy-MM-dd>"`, `h = SHA-256(UTF-8(seed))`;
- байты 0–5: полночь даты в UTC как Unix-миллисекунды, 48 бит big-endian;
- байт 6 = `0x70 | (h[0] & 0x0F)`, байт 7 = `h[1]`, байт 8 = `0x80 | (h[2] & 0x3F)`, байты 9–15 = `h[3..9]`;
- 16 байт читаются как UUID в порядке big-endian (RFC 9562).

### D29. Статус `Skipped` (расширение ТЗ)
В ТЗ статусов два: Cleared и Planned. Пропуск сделан третьим статусом, а не удалением. Удаление при синхронизации
необратимо («удаление побеждает изменение»), а макет предлагает «Отменить» после пропуска. Отмена — обычное
обновление статуса обратно в Planned. Skipped не влияет на баланс и прогноз и не показывается в
`GET /transactions` без явного `status=Skipped`. Удалённая транзакция вхождения тоже считается пропуском.

### D30. Подтверждение
`POST /transactions/{id}/confirm` переводит Planned или Skipped в Cleared, можно передать `amount`, `date`
и (для переводов между валютами) `toAmount`. Для перевода в одной валюте `ToAmount` следует за `Amount`.
`POST /transactions/{id}/skip` переводит только Planned → Skipped.

### D31. Изменение и удаление правила
Изменение правила не трогает уже материализованные транзакции, меняются только будущие вхождения. Удаление правила
мягко удаляет его неподтверждённые Planned-транзакции, а Cleared и Skipped остаются в истории.

### D32. Финансовый месяц
Финансовый месяц называется по месяцу, в котором начинается: при `FirstDayOfMonth = 5` период «2026-10» длится с 5 октября
по 4 ноября. Бюджет хранит первое число этого месяца. Если пользователь меняет `FirstDayOfMonth`, все периоды
(и прошлые) пересчитываются по новому дню: история не хранит старый день начала.

### D33. Валюта бюджета
Бюджет запоминает базовую валюту пользователя на момент создания (`Budget.Currency`). Все суммы бюджета, его линий
и взносов в цели хранятся в ней. Смена базовой валюты старые бюджеты не конвертирует.

### D34. API бюджета: целиком на месяц
`PUT /budgets/{yyyy-MM}` создаёт бюджет или заменяет его план. Линии и взносы, которых нет в теле запроса, удаляются.
Совпадение ищется по `id`, а без него — по категории (или цели). Перенести существующую линию на другую категорию нельзя
(422 `budget_line_category_locked`): нужно удалить её и добавить новую. Так пара (бюджет, категория) остаётся уникальной
на каждом шаге обновления. Для синхронизации (фаза 4) бюджет, линия и взнос остаются отдельными сущностями с собственными id.
`GET /budgets/{month}/summary` для месяца без бюджета отвечает 404.

### D35. Какой линии засчитывается трата
Трата идёт в самую конкретную линию: сначала линия своей категории, затем линия родительской категории, иначе
«Вне бюджета». Если есть линии и у «Транспорта», и у «Такси», то такси считается только в «Такси», а автобус — в
«Транспорте». Двойного счёта нет: сумма по линиям плюс «Вне бюджета» равна всем тратам месяца.
Учитываются только проведённые (Cleared) расходы. Переводы тратами не считаются.

### D36. Перенос остатков (Rollover)
Флаг `Rollover` ставится на линию месяца M: её неистраченный остаток (только положительный, перерасход не переносится)
добавляется к лимиту линии той же категории в месяце M+1. Цепочка тянется по последовательным месяцам с бюджетом в
той же валюте, не дальше 12 месяцев назад. Месяц без бюджета или без линии этой категории обрывает перенос.

### D37. Проценты и статусы линии
`Percent = Spent / (Planned + CarriedOver) × 100` с одним знаком. При нулевом лимите процента нет (`null`).
Статус Warning — от 80% включительно, Over — больше 100%. Трата при нулевом лимите — Over.
Траты конвертируются в валюту бюджета по курсу на дату транзакции. Суммирование идёт группами
«категория × валюта × день», округление один раз на группу.

### D38. Прогресс цели
- Если у цели задан `LinkedAccountId`, прогресс равен балансу счёта, переведённому в валюту цели по сегодняшнему курсу.
- Иначе прогресс — сумма проведённых переводов с `SavingsGoalId` этой цели: `ToAmount` в валюте счёта-получателя,
  пересчитанный по курсу на дату перевода.
- Пометить целью можно только перевод (`savings_goal_only_for_transfers`).

### D39. Рекомендуемый взнос
`MonthsLeft` — число финансовых месяцев от текущего (или планируемого в бюджете) месяца до месяца, в который попадает
`TargetDate`, не включая его; минимум 1. `RecommendedMonthly = ⌈(Target − Current) / MonthsLeft⌉`: округление вверх
до копейки, чтобы цель гарантированно достигалась. Просроченная цель (`IsOverdue`) предлагает весь остаток сразу.
У целей без даты и у выполненных рекомендации нет. В сводке бюджета рекомендация считается для месяца бюджета.

### D40. Дата выполнения цели
Для подписи «выполнена в сентябре» добавлено поле `SavingsGoal.CompletedOn`. Если цель отмечена выполненной без даты,
подставляется сегодняшняя (по часовому поясу пользователя). Также у цели есть `Color` и `Icon`, как у счетов.

### D41. Шаблон бюджета
`GET /budgets/{month}/template` возвращает черновик. В нём доход и линии прошлого месяца, а по каждой открытой цели —
рекомендуемый взнос (если у цели есть дата) или взнос прошлого месяца. Черновик ничего не сохраняет. Так
рекомендация «предлагается при создании бюджета». `POST /budgets/{month}/copy-from-previous` копирует прошлый месяц
как есть (кнопка «Из сентября»).

### D42. Ограничения на удаление (дополнение к D11)
- Счёт нельзя удалить, пока его используют регулярные правила (409 `account_has_recurring_rules`). Если счёт привязан
  к цели, привязка при удалении снимается.
- Категорию нельзя удалить, пока её используют правила (`category_has_recurring_rules`) или линии бюджета
  (`category_in_budget`). Тип у неё в этих случаях тоже менять нельзя.
- Цель нельзя удалить, если на неё ссылаются бюджеты, правила или переводы (409 `goal_in_use`); её можно отметить выполненной.

## Фаза 3: прогноз и аналитика

### D43. Окно прогноза
Симуляция всегда начинается сегодня (по часовому поясу пользователя) с балансов на конец сегодняшнего дня по проведённым
операциям. `from` только обрезает начало выдачи и не может быть раньше сегодняшнего дня. По умолчанию `to` = сегодня + 3 месяца,
максимум — сегодня + 24 месяца (иначе 400 `horizon_too_long`). Помимо `GET /forecast` есть `POST /forecast` с теми же
параметрами в теле: так удобнее передавать сценарий «что если».

### D44. Какие счета участвуют
В итоговую сумму и в ряды по счетам входят только счета с `IncludeInTotals`. Дополнительно симулируются (но не входят в итог)
счета, привязанные к открытым целям, и счета из операций «что если». Перевод на счёт вне симуляции меняет только сторону
симулируемого счёта.

### D45. Учтённые операции без двойного счёта
- Проведённые операции с датой в будущем.
- Planned-операции. Просроченные (дата раньше сегодня) переносятся на сегодня: платёж ещё ожидается.
- Вхождения активных правил с сегодняшнего дня до конца симуляции, кроме уже материализованных. Транзакция вхождения в
  любом статусе, в том числе удалённая или Skipped, означает, что вхождение уже учтено. Пропущенное вхождение в прогноз не попадает.

### D46. Переменные расходы — уточнения
Алгоритм из ТЗ дополнен так, чтобы платежи не считались дважды:
- В месяцах с бюджетом из лимита каждой линии вычитаются уже учтённые операции её категорий в этом месяце
  (Planned, регулярные, будущие проведённые; привязка к линии — как в D35), остаток берётся не меньше нуля.
  Иначе линия «Аренда 900» и правило «Аренда 900» списали бы 1 800.
- Категории без линии в месяце с бюджетом переменных расходов не дают («используются его линии»).
- Медиана считается по месяцам без операций, созданных регулярными правилами: эти правила симулируются отдельно.
  Это и есть «за вычетом трат, покрытых регулярными правилами».
- В медиану берутся только полные финансовые месяцы, начавшиеся не раньше первой операции пользователя. Новый пользователь
  иначе получил бы медиану из нулей. Нет таких месяцев — нет переменных расходов.
- В текущем месяце без бюджета ожидается `max(0, медиана − уже потрачено в этом месяце)` по каждой категории.
- Сумма месяца переводится в валюту счёта списания по последнему курсу и делится поровну по дням (`Money.Allocate`, без потери копеек).
  В текущем месяце — по оставшимся дням, включая сегодня, в будущих — по всем дням месяца.
- Счёт списания — `DefaultSpendingAccountId`. Если он не задан, берётся первая неархивная дебетовая карта или наличные
  среди счетов в итоге. Если и таких нет, переменные расходы не моделируются. Какой счёт использован, видно в ответе.
- Расчёт по месяцам возвращается в `variableSpending` (сумма и источник: `CurrentBudget`, `Budget` или `History`), чтобы
  было видно, на чём основан прогноз.

### D47. Проценты по вкладам и накопительным счетам
Базис actual/365: в день начисляется `ставка / 100 / 365`. Порядок операций за день: начисленные за прошлые дни проценты
выплачиваются в дату выплаты, затем применяются операции дня, затем начисляются проценты за день на остаток к концу дня.
- `Monthly` / `Quarterly`: сложные проценты, капитализация каждые 1 / 3 месяца от `OpenDate`.
- `None`: простые проценты, выплачиваются ежемесячно от `OpenDate` и сами проценты не приносят.
- `AtEnd`: простые проценты, выплата в `MaturityDate`. Если даты погашения нет — раз в год от `OpenDate`.
- Проценты не начисляются до `OpenDate` и после `MaturityDate` (в дату погашения выплачивается остаток) и не начисляются
  на отрицательный баланс.
- Проценты за часть текущего периода до сегодняшнего дня оцениваются по сегодняшнему балансу (история баланса за этот отрезок
  не восстанавливается). Выплата округляется до копейки один раз (ToEven).

### D48. «Что если»
Операция задаётся датой, счётом, суммой со знаком (minor units валюты счёта; минус — деньги уходят со счёта) и необязательной
подписью. В query: `extraOneOff=yyyy-MM-dd|сумма|accountId[|подпись]`, параметр можно повторять. Дата должна попадать в окно прогноза.
Ответ содержит базовый прогноз и `scenario`: итоговый ряд, тревоги, цели и разницу итога на последний день. Ничего не сохраняется.

### D49. Тревожные точки
Тревоги проверяются по дням на отрезке [from, to], а не только в точках выборки, чтобы не пропустить провал внутри месяца:
- итог (в базовой валюте) ниже порога пользователя (`lowBalanceThreshold`, по умолчанию 0);
- счёт списания (в базовой валюте) ниже порога — только при пороге больше 0. Порог на все счета не применяется: в макете
  «Все счета выше порога» относится к основному счёту, а кошелёк с 50 Br иначе сигналил бы всегда;
- любой счёт в итоге, кроме кредитных карт, ниже нуля;
- кредитная карта за пределами `CreditLimit` (без лимита тревоги нет: отрицательный баланс карты — норма).

Последовательные тревожные дни сливаются в один эпизод: начало, конец, самая низкая точка и её дата. По каждому счёту
дополнительно отдаётся минимум за период («Минимум на карте…»).

### D50. Цели к сроку
- Симуляция продлевается до самой поздней `TargetDate` открытых целей, но не дальше 24 месяцев. Ряды в ответе при этом
  обрезаются по `to`.
- Цель с привязанным счётом прогнозируется по балансу этого счёта. Цель без счёта — по текущей сумме плюс будущие переводы,
  помеченные этой целью (Planned, регулярные, будущие проведённые).
- Взносы из бюджета (`BudgetGoalAllocation`) — это план, а не движение денег, поэтому в прогноз они не попадают.
  Чтобы прогноз цели учитывал регулярные взносы, их нужно оформить регулярным переводом.
- Цель оценивается на `TargetDate`. Просроченная — на сегодня, без даты — на `to`, со сроком за пределами 24 месяцев — на конец
  симуляции (`targetBeyondHorizon = true`).
- В ответе: прогноз суммы, хватает или нет, недостача, дата достижения, запас в днях («с запасом 2 недели») и
  `extraMonthlyNeeded` — сколько добавлять в месяц («+115 Br в месяц решат»). Считается по правилу месяцев из D39 и
  округляется вверх.

### D51. Курс в прогнозе
Как в ТЗ, весь прогноз пересчитывается по последнему известному курсу (на сегодня), для любой будущей даты.

### D52. Аналитика: общие правила
Учитываются только проведённые доходы и расходы. Переводы, Planned и Skipped не учитываются. Каждая операция конвертируется в
базовую валюту по курсу на свою дату. По умолчанию период — текущий финансовый месяц. Изменение в процентах равно `null`, если в
прошлом периоде было 0 (в UI — «новое»).

С каким периодом сравнивается (`analytics/categories`, `analytics/compare`):
- целые финансовые месяцы — с тем же числом месяцев перед ними;
- период с начала месяца — с теми же днями прошлого месяца: «5–22 окт» сравнивается с «5–22 сен», как «−8,4% к сентябрю» в макете.
  Если в прошлом месяце дней меньше, период обрезается по его концу;
- любой другой период — с тем же числом дней непосредственно перед ним.

В разбивке по категориям корневая категория включает свои дочерние (`amount` = свои траты + дочерние, `directAmount` —
только свои). Доля считается от итога периода.

### D53. Динамика по месяцам
`analytics/monthly?months=N` возвращает N последних финансовых месяцев, включая текущий (`isCurrent`, на графике со штриховкой).
С `categoryId` считается эта категория вместе с подкатегориями; доход это или расход, определяет тип категории.

### D54. Net worth
«Сумма балансов всех счетов» трактуется как сумма счетов, входящих в итог (`IncludeInTotals`), — так же, как «общий капитал»
на главной. С `includeExcluded=true` учитываются все счета. Точка — конец финансового месяца, для текущего месяца — сегодня.
Баланс на точку конвертируется по курсу на её дату. Счёт учитывается с самой ранней из трёх дат: создания, `OpenDate`,
первой операции. Иначе счёт, заведённый сегодня, «существовал бы» и год назад.

### D55. Средние траты
Считаются по прошедшей части периода: будущие дни текущего месяца не размывают среднее. В неделю = в день × 7,
в месяц = в день × 30,4375 (365,25 / 12). Округление ToEven до копейки.

### D56. Крупнейшие траты
Сортировка по сумме в базовой валюте по курсу на дату траты, так что траты в разных валютах сравниваются корректно.
`limit` от 1 до 50, по умолчанию 10.

## Фаза 4: синхронизация

Протокол для клиента описан в [`sync.md`](sync.md).

### D57. Что синхронизируется
Типы сущностей: `account`, `category`, `savingsGoal`, `recurringRule`, `budget`, `budgetLine`, `budgetGoalAllocation`,
`transaction` и `settings`. Последний тип в ТЗ не назван. Настройки (базовая валюта, день начала месяца и т. д.) нужны
клиенту офлайн и могут меняться с другого устройства, поэтому у `User` появилась `Version` из той же глобальной
последовательности. Настройки идут в pull как сущность `settings` с id пользователя, и их можно менять через push
(полная замена; удалять нельзя). Payload в push и `data` в pull имеют одну форму. Серверные поля в `data`
(`systemCode`, `email`) при push игнорируются.

### D58. Обработка push
Весь батч выполняется в одной транзакции под блокировкой пользователя. Поэтому два устройства, которые одновременно
подтверждают одно вхождение с детерминированным id, не создают конфликт ключей: второе получает обычное обновление.
- Изменения применяются в порядке зависимостей: upsert'ы от родителей к детям, удаления от детей к родителям.
  Иерархия категорий для удалений берётся из БД, потому что у удаления нет payload.
- Каждое изменение проходит через те же writer'ы и валидаторы, что REST, и сохраняется отдельно. Ошибка одного изменения
  откатывает только его (EF Core savepoint) и попадает в `rejected` с кодом.
- Неожиданное исключение логируется, изменение отклоняется с `internal_error`, остальные продолжают применяться.
- Удаление сущности, которой у пользователя нет (никогда не было или она чужая), принимается со статусом `Ignored`:
  удалять нечего, и клиенту не нужно повторять запрос.

### D59. Идемпотентность
Принятые изменения записываются в журнал `sync_change_logs` с ключом `(user, entity id, clientUpdatedAt)`.
`clientUpdatedAt` приводится к UTC и обрезается до микросекунд, как его хранит PostgreSQL, иначе повтор не совпадал бы
с журналом. Повтор возвращает исходный результат (`Duplicate`) и не применяется, даже если payload отличается.
Отклонённые изменения в журнал не пишутся: повтор оценивается заново, ведь за это время могла прийти, например, нужная
категория. Журнал хранится 90 дней, его чистит ежедневная задача `sync-log-cleanup` (03:30 UTC).

### D60. Конфликты
Как в ТЗ: «последняя запись побеждает» в порядке прихода на сервер. `clientUpdatedAt` для разрешения конфликтов не
используется, только для идемпотентности. Удаление окончательно: upsert удалённой сущности отклоняется с `entity_deleted`,
и клиент удаляет её у себя. Push с данными, совпадающими с сохранёнными, возвращает `Unchanged` и не создаёт новую версию.

### D61. Pull без пропусков
Изменения пользователя получают версии под его блокировкой, поэтому версии коммитятся строго по возрастанию.
Все таблицы читаются в одной транзакции `REPEATABLE READ`: снимок содержит непрерывный префикс версий, и курсор
`nextCursor` = последняя отданная версия ничего не пропускает. Это проверяет интеграционный тест с параллельными
записями: при выключенной блокировке он падает. Удалённые сущности отдаются с `deleted: true` и `data: null`.
`limit` от 1 до 1000, по умолчанию 500.

### D62. Бюджет в синхронизации
REST сохраняет бюджет месяца целиком (D34), а sync работает с бюджетом, линией и взносом как с отдельными сущностями.
Месяц и валюта бюджета, бюджет и категория линии, бюджет и цель взноса после создания не меняются.
Уникальность (месяц, категория в бюджете, цель в бюджете) та же, что в REST. Удаление бюджета удаляет его линии и взносы,
и они приходят в pull как удалённые.
